## Current State
`BattleState`/`PokemonSlot`/`SideConditions` carry exactly what M4's hand-crafted `default_eval` needs (HP/fainted/status/types/`boost_spe`/hazards-as-presence-or-stack). `encode()`'s 665-dim vector needs substantially more per Pokemon (species/item/ability/protect_counter, all 7 boost stats, a movedex-derived move summary) and per-state (weather/terrain, full 8-token hazard richness). None of that exists yet. `VECTOR_LEN` confirmed live at 665 (`.venv/bin/python -c "from battle_engine import encoding; print(encoding.VECTOR_LEN)"`).

## Gaps
1. **The plan's file-hint for `movedex_table.hpp` doesn't hold.** It says the table "has per-move-id lookups you'll need for the move-summary features `encode()` computes" — checked directly: `MovedexEntry` has `base_power`/`type`/`priority` (covers `max_base_power`, `move_types`, `has_priority`) but **not** `heal`, `sideCondition`, `selfSwitch`, `target`, or `boosts` — the fields `has_recovery`/`has_hazard_setup`/`has_setup_boost`/`has_pivot` need. `movedex_table.hpp`/`.cpp` and their generator (`scripts/dump_movedex.py`) are **not** in this phase's file scope, so extending them isn't an option here. Resolved via a design decision (below): compute the move summary once in Python (`mcts_player.py`, in scope) by directly reusing `encoding._move_summary_features` — the already-verified derivation — rather than re-deriving a second, less-complete copy in C++. This is safe for Phase 5's later per-node PUCT use too: Tier 1's forward model never mutates a Pokemon's moveset/item/ability, so a value computed once at translation time stays correct through every simulated node in the search tree.
2. **`test_native_legality.py`/`test_mcts_player.py`'s `_battle()` fixtures don't set `battle.weather`/`battle.fields`.** Those files are out of file scope (can't add the attributes to their fixtures) and DW-4.2 requires them to keep passing unchanged. `battle_state_from_poke_env` reads these via `getattr(battle, "weather", {})`/`getattr(battle, "fields", {})` rather than direct attribute access — for a real `AbstractBattle` these are always real attributes (never hits the fallback); for the existing minimal fixtures, the fallback default (`{}`, "no weather/terrain") is the exact real state those fixtures represent anyway.
3. **`encode()`'s two multi-hot type dimensions (own-types, move-type-coverage) are indexed by poke-env's `PokemonType` enum (20 members, alphabetical, includes `THREE_QUESTION_MARKS`/`STELLAR`), not `be::Type`'s (18 members, gameplay-grouped order, no ??? /Stellar).** Verified directly (`list(PokemonType)` dump). A fixed 18-entry permutation table (`kTypeToAllTypesIndex`) mapping each `be::Type` value to its position in the 20-slot Python-order vector is required for bit-for-bit parity; positions 18/19 (???, Stellar) are structurally unreachable from `be::Type` and stay zero, matching real gameplay (no live Tier-1 state ever has a ??? or Stellar-typed active mon).
4. **`_STATUSES`' one-hot order (`BRN,FRZ,PAR,PSN,SLP,TOX`) differs from `be::Status`'s declared enum order (`Brn,Frz,Par,Psn,Tox,Slp`)** — Tox/Slp are swapped. A second small permutation table is required; `None`/`Fnt` both correctly map to "no bit set" (matches `encode()`'s own `status if status != FNT else None` — the table's exclusion of both values reproduces that override without a separate conditional).
5. **A default-constructed `PokemonSlot` is not equivalent to `encode()`'s "unknown" sentinel.** `hp_fraction` defaults to `1.0f` (chosen for M4's `default_eval`, which never reads an unrevealed slot's `hp_fraction` at all) but `PokemonView.unknown()` requires `0.0`. Every other field already defaults to the correct zero. Resolved by having `encode_pokemon_slot()` short-circuit to an explicit all-zero 91-vector for `!revealed`, rather than reading struct fields at all in that case — avoids touching `PokemonSlot`'s existing default (out of scope to re-justify, and `cpp/tests/test_battle_state.cpp`, which would need a new test for such a change, is itself out of file scope).
6. `opp_remaining_fraction` needs no new field: `(6 - count(fainted, opp_team)) / 6` is already fully derivable from the existing 6-slot array (an unrevealed opponent slot's `fainted` defaults `false`, matching Python's exclusion of never-revealed mons from the count).

## Code Standards
Read in full; the load-bearing rules for this phase: never assume API behavior (drove the `PokemonType`/`be::Type` and `_STATUSES`/`be::Status` permutation verification above via direct interpreter checks, not inspection); never silently drop a simplification (every design decision below is named inline in the new header/impl comments, not just here); C++ header comments state the alternative considered and why it lost; `is_valid()`-style predicates for state invariants, not exceptions in the hot path — `encode_native()` itself is a boundary function (mirrors `battle_view_from_poke_env`'s own `ValueError`), not a per-transition invariant check, so a thrown `std::invalid_argument` for "no active Pokemon" is the right shape, matching `PolicyWeights::load`'s existing `std::runtime_error`-on-malformed-input precedent.

## Design Decisions

**Move-summary derivation: compute once in Python, store as data on `PokemonSlot`, not re-derive in C++ from `movedex_table.hpp`.**
- Alternative considered: port `_move_summary_features`'s dex-flag logic into C++, reading `lookup_movedex()`. Rejected — `MovedexEntry` doesn't carry the needed flags and `movedex_table.hpp`/generator are out of file scope (see Gaps #1); extending them would silently exceed this phase's scope.
- Chosen: `mcts_player.py` (in scope) calls `encoding._move_summary_features(list(mon.moves.keys()))` directly — the exact function `encode()`'s own live adapter already uses — and packs the result into new `PokemonSlot::move_summary` fields. `encode_native()` only ever *reads* this pre-computed data.
- Correctness argument: guarantees bit-for-bit parity by construction (same function, same input) rather than by porting-then-hoping-they-agree. Safe under Phase 5's forward-model simulation because moveset/item/ability are static for a Pokemon's whole battle in this project's current (Tier 1) mechanics scope — nothing in `forward_model.cpp` ever mutates them, so a value fixed at translation time remains correct at every simulated tree node.
- Same reasoning extended to weather/terrain (`encoding._poke_env_weather`/`_poke_env_terrain`, reused directly rather than re-derived) and to item (`encoding._poke_env_item`, reused for its unknown-token sentinel set) — this phase's Python-side additions are adapters over already-verified functions, not new parallel logic.

**Hazards: NOT reused from `encoding._poke_env_hazards`, unlike the above.** Per the plan's own Approach notes, `SideConditions` must store full per-token turn/stack data for all 8 tokens (`mcts_player.py`'s `_side_conditions` reads 6 raw turn numbers + the existing 2 stack counts directly off `battle.side_conditions`), and `encode_native()` (C++) re-derives the single-most-recent view on demand — porting `_poke_env_hazards`'s algorithm (rank turn-tracked tokens by turn number, first-wins on a tie to match Python `max()`'s tie-break; fall back to a stack-tracked token, spikes before toxic spikes, when no turn-tracked token is active) directly into C++, not reusing the Python reduction. This is the one place data crosses into C++ *unreduced*, matching `BattleState`'s existing "one ordering stored, view computed on demand" invariant.

**`encode_native()` lives in `battle_state.hpp`/`.cpp`, not a new file.** File scope for this phase doesn't include a new header; conceptually this is the struct's "canonical read-out," consistent with keeping a stored representation next to its one supported view (same rationale the plan's Approach notes already give for the hazard reduction).

**`is_valid()` left untouched.** Extending its invariant checks to the 6 new boost fields isn't part of this phase's `Produces` contract, and `cpp/tests/test_battle_state.cpp` (which would need a new test for such an extension) is out of file scope. New fields default to values that already satisfy the existing checks, so this is a no-op for `is_valid()` either way.

**Species-sorted bench view:** computed on demand inside `encode_native()` from `state.my_team` (skip `my_active_slot`, skip unrevealed, sort by `species` — `base_species` identity per the plan's explicit constraint, populated in `mcts_player.py` via `mon.base_species` directly), padded to `kMaxBench=5` with a default-constructed (`revealed=false`) sentinel slot. Opponent's bench is never encoded at all (matches `encode()`'s own asymmetry — only `opp_active` + `opp_remaining_fraction`), so no opponent-side sort is needed this phase.
